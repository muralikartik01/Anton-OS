argument-hint: [--source databricks:<cat>.<schema> | azuresql:<schema> | postgres:<schema>] [--target databricks] --landing <cat>.<schema> [--bronze <cat>.<schema>] [--silver <cat>.<schema>] [--scope t1,t2] [--jdbc-secret-scope <name>] [--dry-run]
---

Start a new `legacy_to_bronze_silver_migration` run (`workflows/templates/legacy-to-bronze-silver.yaml`) with arguments: $ARGUMENTS

1. Parse the arguments. `--landing <catalog>.<schema>` is required — if missing, ask for it; do not guess. Defaults: `--bronze` = `<landing catalog>.bronze`, `--silver` = `<landing catalog>.silver`. Never hardcode catalog/schema names from examples.
   - `--source` is `databricks:<cat>.<schema>` (data already in landing; this is the default when `--source` is omitted) or `postgres:<schema>` (read from the Azure Database for PostgreSQL named by the `DB_KIT_PG_*` env vars, then loaded into landing) or `azuresql:<schema>` (read from the Azure SQL database named by the `DB_KIT_AZSQL_*` env vars, then loaded into landing). Any other source type: stop and say which are supported.
   - `--target` defaults to `databricks`; any other target: stop and say only `databricks` is supported in Phase 1.
   - `--dry-run`: run only `discovery` → `assessment` → `migration_blueprint` → approval gate → `artifact_generation` → `documentation`, then stop. Nothing is executed on Databricks, so no Databricks workspace or `DB_KIT_DBX_*` variables are needed. It requires `--source azuresql:<schema>` or `postgres:<schema>` (a `databricks` source needs the workspace for discovery; if given, stop and say so). The `--landing`/`--bronze`/`--silver` names are only used as names in the generated code. Record `dry_run: true` in `input_parameters`.
   - For `azuresql` or `postgres`, `--jdbc-secret-scope` (a Databricks secret scope holding the JDBC user/password) is required for the landing load — ask for the scope and key names; never ask for the password itself. **Exception, `--dry-run`:** do not ask. If no scope is given, use the placeholders scope `db-kit-demo`, keys `jdbc-user` / `jdbc-password`, and say in the blueprint that they are placeholders to replace before a real run.
2. Confirm the needed MCP servers respond: `db-kit-context`, `db-kit-databricks` (skip in `--dry-run`) (`list_tables` on the landing schema, or on the source schema for a databricks source) and, for an `azuresql` / `postgres` source, `db-kit-azuresql` / `db-kit-postgres` (`list_tables` on the source schema). If the Databricks env vars are missing or the call fails, stop and report — set nothing up on your own and never ask for the token in chat.
3. Generate `run_id` (`mig-<project-id>-<timestamp>`) and create `observability/run-records/<run_id>.yaml` per `observability/run-records/_schema.md` with `workflow_id: legacy_to_bronze_silver_migration`, `state: created`, and `input_parameters` holding the resolved source (`type` + location), target, landing/bronze/silver names, secret scope name and scope.
4. Run the steps in order: `discovery` → `assessment` → `migration_blueprint`, using the agent and skills named in the template. Update the run record (`steps`, `current_step`, `output_refs`) after every step.
5. **Approval gate (Stage 4).** Present `blueprint.md` and `source-to-target-mapping.yaml` (plus the mapping validation result and the assessment's risks) and STOP. Set `state: awaiting_approval`. Proceed only on the human's explicit approval in this conversation; then append to the run record `approvals`: `{stage: migration_blueprint, approved_by: <the user>, approved_at: <now>, scope: <summary>}`. Never write this entry on your own initiative.
6. Run `artifact_generation` (Transformation Agent — generates only; includes `landing/` for an azuresql or postgres source), `documentation` (one doc per notebook), then `validation` (Validation Agent — first materializes the approved SQL with `execute_statement(sql, run_id, confirm=true)`, landing first for an azuresql or postgres source, then runs checks), then `review`.
   **Dry run:** after `documentation`, set `state: completed` with `completion_summary` noting `dry_run` (validation and review not run, nothing executed), list the generated paths (`artifacts/generated-code/<project-id>/<run_id>/{landing,bronze,silver,config,docs}/`), and stop. Do not call `execute_statement`.
7. If any step cannot complete, set `state: blocked`, record the reason in the step's `notes`, and stop. Resume later with `/db-kit-resume <run_id>`.
8. On completion set `state: completed`, write `completion_summary`, and report the path to `artifacts/reports/<project-id>/<run_id>/migration-report.md` with a short summary: what was migrated, validation pass/fail/blocked counts, review score, open issues. Stage 8 (release) is a note only — no production write exists to authorize.

Safety: `hooks/pre-execution/` and `hooks/validation/require_blueprint_approval.py` apply to every MCP call. Only the Validation Agent calls `execute_statement`.
