# Cluster sizing forecast heuristics

This table is the cited reference used by the `cluster-sizing-forecast` forecaster. Values mirror the skill README and are intentionally conservative for first-run sizing.

| Heuristic | Value | Rationale | Source `[O]` (URL) |
| --- | --- | --- | --- |
| Input partition target | 128 MB per file-read partition (`spark.sql.files.maxPartitionBytes = 134217728`) | Converts source `sizeInBytes` into read parallelism while avoiding tiny-task overhead. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Shuffle partition target | 64 MB AQE advisory, modeled conservatively as 128 MB per shuffle partition | AQE coalesces and splits shuffle partitions around the advisory target; 128 MB is the forecast sizing anchor used for shuffle partition counts. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Tasks per core | 2–3 tasks per CPU core; use 2.5 as midpoint | Spark recommends over-partitioning relative to cores so scheduler latency, I/O stalls and stragglers do not leave CPUs idle. | [O] https://spark.apache.org/docs/latest/tuning.html |
| Memory per core baseline | 4 GB/core baseline; 6–8 GB/core for shuffle-, MERGE- or join-heavy work | Spark's unified memory model leaves only part of heap for execution/storage; shuffle-heavy work needs extra headroom for sort buffers, aggregation state and spills. | [O] https://spark.apache.org/docs/latest/tuning.html |
| Broadcast hash join automatic threshold | Dimension side `< 10 MB` uses the default automatic broadcast threshold and adds no shuffle | Spark's default `spark.sql.autoBroadcastJoinThreshold` is 10 MB, allowing small relations to avoid sort-merge shuffle. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Broadcast-hint candidate band | Dimension side `10 MB–2 GB` is a candidate for explicit broadcast hint only after sanity-checking memory | Above Spark's automatic threshold, small dimensions may still be broadcast manually; cap the forecast band before spill risk dominates every executor. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Sort-merge join cutoff | Both sides `> 2 GB` are forecast as SMJ and shuffle both sides | Large relations should not be broadcast; forecast sort-merge join and allow AQE to downgrade to broadcast only if runtime statistics prove safe. | [O] https://docs.databricks.com/aws/en/optimizations/aqe |
| Parquet decompression / in-memory expansion | ×3 sizing factor for shuffle and memory estimates | Forecast from compressed `sizeInBytes`; Parquet commonly expands in memory, so the model uses a conservative lower-bound expansion factor. | [O] https://docs.databricks.com/aws/en/tables/operations/table-details |
| MERGE / Upsert / SCD2 shuffle estimate | `source_GB × 3 + matched_target_GB × 3` | Delta MERGE joins source to target and rewrites touched files; partition pruning reduces `matched_target_GB`, otherwise assume full target scan. | [O] https://docs.databricks.com/aws/en/delta/best-practices |
| Low Shuffle Merge mitigation | Size for unmitigated MERGE, but note Low Shuffle Merge as a reducer | Low Shuffle Merge processes unmodified rows separately and reduces shuffled data, but the forecast remains conservative before first run. | [O] https://docs.databricks.com/aws/en/optimizations/low-shuffle-merge |
| Deletion vectors mitigation | Treat as rewrite deferral, not zero-cost rewrite elimination | Deletion vectors avoid immediate Parquet rewrites for row-level changes, but cleanup/OPTIMIZE work can still occur later. | [O] https://docs.databricks.com/aws/en/tables/features/deletion-vectors |
| Skew risk signal and hedge | Key cardinality `< 10×` shuffle partitions, hot keys or NULL-heavy keys → +20–30% executor memory | Low-cardinality keys create uneven partitions; AQE can split some skew, but memory headroom protects stragglers and unsupported cases. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Aggregation/window memory hedge | Low-cardinality `GROUP BY` / `PARTITION BY` or unbounded window frame → +50% executor memory | Large per-key state and sort/window buffers increase execution-memory pressure. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| COUNT DISTINCT shuffle cost | `COUNT(DISTINCT ...)` = 2 shuffles | Distinct aggregation first groups/deduplicates, then counts, so the forecast adds the input to shuffle volume twice. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Simple ETL throughput prior | 100–500 GB/hr per 100 cores | Used for scan/filter/write jobs with no wide distributed operations. | [O] https://www.databricks.com/blog/best-practices-cost-management-databricks |
| Sort-merge join throughput prior | 30–100 GB/hr per 100 cores | Network shuffle and sorting dominate balanced SMJ jobs. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| MERGE without partition pruning throughput prior | 10–50 GB/hr per 100 cores | Full target scan plus rewrite makes unpruned MERGE the slowest batch class. | [O] https://docs.databricks.com/aws/en/delta/best-practices |
| MERGE with partition pruning throughput prior | 50–200 GB/hr per 100 cores | Adding partition constraints to the MERGE condition reduces target search space and rewrite scope. | [O] https://docs.databricks.com/aws/en/delta/best-practices |
| Window-heavy throughput prior | 20–80 GB/hr per 100 cores | Large windows require ordering and buffering, making them sort/memory bound. | [O] https://spark.apache.org/docs/latest/sql-performance-tuning.html |
| Photon multiplier | 2–5× runtime / price-performance improvement for SQL/DataFrame joins, aggregations and large scans | Photon accelerates supported SQL and DataFrame operators; enable for substantial ETL, disable for trivial or unsupported UDF/RDD-heavy work. | [O] https://docs.databricks.com/aws/en/compute/photon |
| Node family: memory optimized | Use E-series for shuffle/MERGE/join-heavy or spill-prone jobs; prefer fewer larger nodes | Databricks recommends larger instances and fewer workers for complex ETL to reduce shuffle overhead and add memory. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| Node family: compute optimized | Use F-series for CPU-bound, streaming or maintenance workloads with low memory-per-core needs | Compute-optimized nodes fit workloads where CPU is limiting and shuffle memory is not. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| Node family: general purpose | Use D/DS-series for balanced ETL defaults | General-purpose nodes are the default fit when neither memory nor CPU dominates. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| Single-node rule | If `total_source_GB < 1` and there are no distributed joins, MERGE, aggregations or windows, use single-node | Lightweight workloads without distributed shuffle do not need a multi-worker cluster. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| Autoscale rule | Use autoscale when projected runtime is `> ~30 min` and stage parallelism is variable; use fixed/pool for short or SLA-critical jobs | Autoscaling helps variable workloads but scale-up latency can hurt short or latency-sensitive jobs. | [O] https://docs.databricks.com/aws/en/compute/configure |
| Spot by criticality | Low criticality → spot workers; medium → spot workers with on-demand fallback; high criticality or SLA `< 2 h` → on-demand workers | Spot capacity can lower cost but may be reclaimed; production/SLA jobs need reliability. | [O] https://docs.databricks.com/aws/en/compute/configure |
| Driver availability | Driver is always on-demand; never use a spot driver | Databricks warns not to use spot pools for the driver because driver loss terminates the cluster. | [O] https://docs.databricks.com/aws/en/compute/configure |
| Jobs Compute pricing | Use current Jobs-Compute DBU price; price rows are SCD2 with `price_start_time` and `price_end_time` | Pricing must be read at runtime from `system.billing.list_prices`; current row has active effective dates. | [O] https://docs.databricks.com/aws/en/admin/system-tables/pricing |
| Usage correction handling | Net DBUs by treating `RETRACTION` rows as negative before computing analog DBU/hr | Billing usage includes correction records, so analog actuals must sum signed usage quantities. | [O] https://docs.databricks.com/aws/en/admin/system-tables/billing |
| Fleet norm source | Use `system.compute.clusters` to confirm observed node types and autoscale ranges | Fleet norms keep forecast recommendations inside node types actually used by the SRD job fleet. | [O] https://docs.databricks.com/aws/en/admin/system-tables/compute |
| No hardcoded Spark sizing configs | Do not emit `spark.executor.memory`, `spark.executor.cores` or `spark.dynamicAllocation.*` | Databricks compute best practices warn that hardcoded Spark configs override built-in optimization and can conflict with Databricks autoscaling. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| Forecast-to-measure loop | First 2–3 runs should use a fixed cluster, then refine with measured telemetry | Stable first-run telemetry lets the measured sizer/optimizer validate and tighten the conservative forecast. | [O] https://docs.databricks.com/aws/en/compute/cluster-config-best-practices |
| AQE safety net | AQE can coalesce partitions, split skew and convert SMJ to broadcast at runtime, but cannot shrink the chosen cluster size mid-run | The forecast can be conservative because AQE optimizes within the cluster envelope after runtime statistics arrive. | [O] https://docs.databricks.com/aws/en/optimizations/aqe |
| File-count caveat | Use `sizeInBytes / 128 MB`, not `numFiles`, for partition estimate; many tiny files signal OPTIMIZE need | Databricks tunes target file sizes and file count alone does not equal read parallelism. | [O] https://docs.databricks.com/aws/en/tables/tune-file-size |
